## 1. МАКРО-УРОВЕНЬ (Система в целом)

### Назначение системы
**Airport Hub Platform** — распределенная модульная экосистема корпоративного уровня (Enterprise), спроектированная и реализованная для комплексной цифровизации инфраструктуры обслуживания пассажиров и контроля качества операционного персонала аэропорта. Платформа объединяет три ключевых контура:
1. **Централизованная федерация доступа и SSO (Zero-Trust Forward-Auth Gateway):** объединение разнородных внутренних микросервисов под единым шлюзом авторизации с единым каталогом учетных записей, RBAC-моделью с гранулярными правами (включая строгий приоритет запрещающих правил), синхронизацией прав подключаемых модулей на лету (Runtime Permission Sync) и криптографически подписанными мандатами доступа на базе алгоритма RS256.
2. **Омниканальный AI-консьерж с гибридным операторским контуром:** круглосуточная автоматизированная поддержка пассажиров (Web-чат с двусторонними WebSockets, Telegram через прямой клиентский MTProto-протокол, WhatsApp Business Cloud API) на базе LLM-агента с поддержкой RAG по регламентам аэропорта, динамическим трекингом статусов рейсов, распределенным планировщиком напоминаний и стейт-машиной эскалации/возврата диалогов между ИИ и живыми операторами.
3. **Автоматизированная речевая аналитика и контроль качества (Speech QA Pipeline):** пакетная и потоковая обработка аудиозаписей телефонных переговоров, включающая распознавание речи (STT), диаризацию/маппинг ролей участников, детерминированную проверку цитат на галлюцинации (Evidence Validator), многокритериальный скоринг операторов и фоновый пересчет исторических данных при модификации оценочных сценариев.

### Архитектурный паттерн
- **Federated Modular Architecture & Zero-Trust Reverse Proxy:**
  - **Forward-Auth / Subrequest Authentication:** Nginx Gateway перехватывает все запросы к модулям (`/apps/<module>/*`) и выполняет внутренний подзапрос к ядру Hub, пропуская трафик только при наличии валидной сессии и прав с динамической генерацией токена RS256.
  - **Asynchronous Pipeline & Stage Decoupling:** Архитектура речевой аналитики построена на базе 5-стадийного конвейера с изолированными этапами, строгой валидацией артефактов через Pydantic v2 и промежуточной фиксацией состояний.
  - **Event-Driven & In-Memory Task Scheduling:** Асинхронные воркеры на базе Redis Sorted Sets (ZSET) для планирования отложенных сервисных нотификаций и фонового опроса изменений расписания полетов.
  - **CQRS & Hybrid State Storage:** Разделение персистентных сущностей (PostgreSQL: пользователи, аудит, история CRM, справочник рейсов) и оперативного состояния (Redis: черные списки токенов, сессии, подписки, кэши интроспекции, статусы онлайн-присутствия).

### Системные гарантии
- **Concurrency & Non-blocking I/O:** Полностью асинхронный бэкенд на базе `FastAPI` / `Starlette`, неблокирующие пулы соединений к Postgres через `psycopg3` (async connection pool) и `SQLAlchemy 2.0 Async/Scoped Sessions`.
- **Zero-Trust Network Perimeter:** Внутренние микросервисы не публикуют порты наружу. Межмодульное доверие основано на асимметричной криптографии (RS256 Private/Public keypair) с локальной валидацией подписи в модулях и защитой от replay-атак через проверку JTI в Redis.
- **Целостность и идемпотентность данных:** Полный аудит привилегированных действий в формате JSON-дельт (`before_state` $	o$ `after_state`), SHA-256 хэширование полезной нагрузки для дедупликации входящих сообщений от пассажиров, криптографическая верификация вебхуков Meta через HMAC-SHA256.
- **Fault-Tolerance & Graceful Degradation:** Сбои внешних AI-моделей или API мессенджеров изолируются политиками повторных попыток (exponential backoff) и фолбэк-сценариями, не нарушая работу авторизационного ядра и смежных модулей.

### ФУНДАМЕНТАЛЬНЫЕ ПОДСИСТЕМЫ (75% объема раздела)

#### 1. Центральное ядро авторизации, федерации прав и Zero-Trust шлюз (`hub-backend` + `gateway`)

##### Архитектура решения и сквозной поток аутентификации (End-to-End Request Flow)
Ядро реализует федеративную модель доступа к микросервисам без передачи мастер-паролей или долгоживущих токенов во внутренний периметр:
1. Пользователь входит через `POST /api/v1/auth/login`. Сервер генерирует запись сессии в таблице `sessions` PostgreSQL, выставляет HttpOnly-cookie `hub_session` и защитный CSRF-токен (`hub_csrf`), сохраняя дескриптор активности в Redis.
2. При переходе по адресу `/apps/<module_code>/*` Nginx перехватывает запрос через директиву `auth_request /_hub_gateway_authorize`.
3. Внутренний обработчик ядра (`hub-backend/app/api/internal.py`) валидирует сессию, извлекает пользователя с его активными ролями и группами (`selectinload`), вычисляет эффективные права и генерирует короткоживущий токен доступа (`mint_grant`).
4. Токен подписывается асимметричным приватным RSA-ключом по алгоритму **RS256** (срок жизни — 60 секунд, настраивается через `GRANT_TTL_SECONDS`). В заголовках ответа шлюзу возвращаются:
   - `X-Hub-Access-Grant`: подписанный JWT-токен;
   - `X-Hub-Module-Upstream`: целевой внутренний DNS-адрес контейнера (например, `http://airport-demo-flight-feed:8002`);
   - `X-Trace-Id`: сквозной идентификатор трассировки.
5. Nginx динамически проксирует запрос во внутренний апстрим `$module_upstream`, транслируя токен в заголовке `X-Hub-Access-Grant`.
6. Целевой сервис проверяет подпись открытым ключом локально (offline verification) и при необходимости запрашивает интроспекцию `POST /internal/grants/introspect` для исключения отозванных мандатов.

##### Модель данных и алгоритм вычисления эффективных прав (RBAC with Deny-Precedence)
Реляционная схема прав (`app/models/entities.py`) спроектирована с разделением на уровне таблиц связей:
- Сущности: `User`, `Role`, `Group`, `Permission`, `Module`, `AccessGrant`, `SessionRecord`, `AuditEvent`, `LoginEvent`.
- Связующие таблицы: `user_roles`, `user_groups`, а также матрицы прав `user_permissions`, `role_permissions`, `group_permissions` с полем `effect VARCHAR(10) DEFAULT 'allow'`.

**Алгоритм разрешения прав (`app/services/access.py`):**
При расчете контекста доступа (`AccessContext`) объединяются все правила пользователя, его активных групп и ролей:
1. Выполняются три оптимизированных запроса для извлечения пар `(permission_code, effect)` для пользователя, его активных групп и его активных ролей.
2. Иерархия источников правил:
   $$\text{Priority: } \text{User} \succ \text{Group} \succ \text{Role}$$
3. **Абсолютный приоритет Deny:** Внутри каждого уровня и при слиянии уровней действует жесткое правило: если для кода разрешения обнаружен хотя бы один `deny`, право блокируется безусловно, даже если на более низких или высоких уровнях задан `allow`.
4. Это предотвращает случайное получение избыточных прав сотрудником при включении его в широкие группы или назначении типовых системных ролей.

##### Протокол динамической синхронизации прав модулей (Runtime Permission Sync)
Вместо монолитного жесткого кодирования прав всех сервисов в базе Hub, автор разработал распределенный протокол синхронизации:
1. В каталоге `hub-backend/modules-manifest/*.yaml` хранятся технические манифесты модулей (код, название, внутренний URL, URL хелсчека, audience).
2. При старте бэкенда или по ручному триггеру администратора Hub обращается к внутреннему эндпоинту сервиса: `GET /internal/hub/permissions`.
3. Сервис возвращает декларацию своих разрешений, например:
   - Входное право (`kind: "entry"`, строго одно на модуль, транслируется в категорию `platform`);
   - Продуктовые права (`kind: "product"`, права на конкретные экраны и действия внутри модуля).
4. Hub валидирует контракт (уникальность кодов, наличие ровно одного entry-права), сохраняет разрешения в таблицу `permissions` с указанием `origin_module_code`, присваивает их системной роли `super_admin` и фиксирует статус синхронизации (`synced`, `stale` или `error`).

##### Механизмы инвалидации и каскадные черные списки в Redis
Для мгновенного отзыва доступа без ожидания истечения TTL токенов реализована система временных барьеров и черных списков в Redis (`app/core/redis.py`):
- `grant:revoked:<jti>` — немедленный отзыв конкретного выданного токена;
- `session:revoked:<session_id>` — аннулирование сессии при логауте;
- `user:revoke_after:<user_id>` — временной барьер пользователя: все токены, выпущенные до момента смены пароля или блокировки пользователя, отвергаются;
- `module:revoke_after:<module_code>` — временной барьер модуля: инвалидация всех активных грантов модуля при его отключении администратором платформы.

*Кастомная разработка vs библиотеки:* С нуля спроектированы протокол динамической синхронизации прав, алгоритм расчета эффективных прав с приоритетом Deny, связка Nginx `auth_request` с динамическим апстримом и каскадная инвалидация через временные барьеры в Redis. Библиотеки: `FastAPI`, `SQLAlchemy 2.0`, `PyJWT`, `psycopg3`.

#### 2. Многоканальный AI-консьерж и стейт-машина диалогов (`modules/airport-demo`)

##### Конечный автомат диалога (Conversation State Machine & Handoff)
Контур координирует обслуживание пассажиров, предотвращая коллизии между ответами языковой модели и действиями живых операторов.
Состояния треда строго формализованы:
- `ai` — автономная генерация ответов нейросетевым агентом;
- `operator` — агент заблокирован, диалог ожидает ответа дежурного оператора;
- `emergency` — наивысший приоритет (утеря багажа, медицинские инциденты, безопасность), маршрутизация супервизорам.

**Механика безопасного переключения (Hand-off & Resume):**
1. При срабатывании инструмента `request_operator_help` или обнаружении явного запроса человека сервис `OperatorHandoffService` атомарно переводит статус треда в `operator`.
2. Фоновая LLM с нулевой температурой анализирует историю реплик и формирует структурированное резюме ситуации (`structured summary`): суть проблемы, эмоциональный фон, проверенные данные.
3. Пассажирский веб-клиент мгновенно получает push-уведомление через WebSocket о передаче диалога человеку.
4. При закрытии тикета оператором (`return_dialog_to_ai`) статус возвращается в `ai`, но сводка действий оператора инжектируется в системный промпт агента. Это предотвращает повторный опрос пассажира по уже решенным вопросам.

##### Распределенный планировщик задач на базе Redis Sorted Sets (`ReminderSchedulerService`)
Кастомный планировщик отложенных сервисных сообщений:
- В качестве очереди с приоритетом по времени используется **Redis Sorted Set (ZSET)** с ключом `reminders:scheduled`, где `score` — это метка времени исполнения (UNIX timestamp).
- Фоновый воркер с интервалом `REMINDER_POLL_INTERVAL` извлекает готовые задачи по диапазону $[-\infty, \text{now\_ts}]$.
- Извлечение и блокировка выполняются атомарно через конвейер Redis, предотвращая дублирование отправок при наличии параллельных реплик воркера.
- Реализован механизм **Safe-Time Scheduling**: учет часового пояса аэропорта (`Asia/Tashkent`), автоматический перенос ночных напоминаний на утро и взаимное подавление: создание пассажиром `smart reminder` автоматически ставит на паузу регулярную серию сервисных касаний (`fixed touches`).

##### Движок трекинга рейсов и персонализированных подписок (`FlightSubscriptionService`)
- Постоянный мониторинг изменений рейсов (нормализация номеров с префиксом `KIN-`, валидация форматов IATA/ICAO).
- Фоновый воркер отслеживает изменения статусов полетов (смена выхода на посадку, задержка рейса, начало посадки, отмена).
- При обнаружении расхождения формируется персонализированное уведомление на языке пассажира (RU/EN/UZ), которое маршрутизируется в активный канал связи (Telegram или WhatsApp).

##### Векторная база знаний RAG (`rag_knowledge_service.py`)
- База регламентов аэропорта хранится в Markdown-формате в каталоге `data/docs`.
- Векторизация чанков и сохранение в локальный индекс **FAISS**.
- Контроль целостности индекса: сервис рассчитывает SHA-256 хэши исходных файлов и хранит их в `manifest.json`. При обновлении файлов сервис при старте автоматически детектирует рассинхронизацию и перестраивает индекс без прерывания обслуживания входящих запросов.

*Кастомная разработка vs библиотеки:* С нуля разработаны стейт-машина диалогов, планировщик задач на Redis ZSET с поддержкой часовых поясов, детектор изменений расписания полетов и протокол дедупликации сообщений. Библиотеки: `LangChain`, `FAISS`, `redis-py`, `psycopg3`.

#### 3. Распределенный пайплайн речевой аналитики и анти-галлюцинационный скоринг (`modules/analytic-module`)

##### Пятистадийный вычислительный конвейер (Audio Processing Pipeline)
Сервис реализует потоковую и пакетную оценку телефонных разговоров операторов по 5-стадийной схеме:

$$\text{Audio Upload} \longrightarrow \mathbf{STT} \longrightarrow \mathbf{RoleMap} \longrightarrow \mathbf{QA} \longrightarrow \mathbf{Topics} \longrightarrow \mathbf{Scoring} \longrightarrow \text{Storage}$$

1. **STT (Speech-to-Text):** преобразование аудиопотока в структурированный `TranscriptArtifact` с таймкодами и сегментами речи.
2. **RoleMap (Диаризация и маппинг ролей):** разделение сегментов между оператором и клиентом, расчет хронометража (`operator_talk_ratio`, `client_talk_ratio`) и фиксация перебиваний.
3. **QA (Анализ покрытия скрипта):** поиск обязательных элементов диалога (приветствие, идентификация, вежливость).
4. **Topics (Тематическая классификация):** определение категории обращения по каталогу тем.
5. **Scoring (Многокритериальный расчет):** расчет итогового балла (0–100) с учетом весов критериев и критических штрафов.

##### Детерминированный валидатор галлюцинаций цитат (`EvidenceValidator`)
Для полного исключения ситуаций, когда LLM «придумывает» несуществующие нарушения или вымышленные цитаты оператора, автором спроектирован валидатор `EvidenceValidator`:
Каждая находка модели (`Finding`) обязана содержать идентификатор сегмента (`segment_id`) и точную цитату (`quote`). Валидатор проверяет строгое подстрочное вхождение:
```python
if evidence.quote not in segment.text:
    raise EvidenceValidationError(
        stage="qa",
        message=f"Цитата не совпадает с сегментом расшифровки {evidence.segment_id}: {evidence.quote!r}"
    )
```
При несовпадении цитаты результат отбраковывается, инициируя повторный запрос к модели или безопасный перевод в fallback-режим с уведомлением супервизора.

##### Асинхронный диспетчер фонового пересчета (`ScenarioRescoreDispatcher`)
При изменении критериев в сценарии оценки требуется актуализировать скоринг исторической базы звонков. Был реализован неблокирующий диспетчер на базе `threading.Thread`, `threading.Event` и `threading.Lock`:
- Диспетчер работает в постоянном фоновом потоке.
- При публикации новой версии сценария метод `submit(profile)` атомарно обновляет ожидающий профиль и активирует сигнальное событие.
- Поток пробуждается и батчами пересчитывает исторические звонки в фоновом режиме, сохраняя мгновенную отзывчивость REST API аналитики под нагрузкой.

*Кастомная разработка vs библиотеки:* Полностью с нуля написаны архитектура стейт-машины конвейера, строгий алгоритм валидации цитат `EvidenceValidator`, диспетчер пересчета исторических метрик на тредах и версионирование сценариев скоринга. Библиотеки: `Pydantic v2`, `FastAPI`, `OpenRouter API client`.

## 4. СЛОЖНЫЕ ИНЖЕНЕРНЫЕ РЕШЕНИЯ (Engineering Deep-Dive)

### 1. Архитектура распределенного Zero-Trust доступа на базе Nginx `auth_request` и RS256
- **Сложность:** Предоставление единой точки входа к разнородным внутренним SPA и веб-приложениям без дублирования кода авторизации и без прямого доступа модулей к базе данных пользователей.
- **Реализация:** Реализован паттерн шлюзовой пред-авторизации: при обращении к `/apps/<module>/*` Nginx выполняет подзапрос `/_hub_gateway_authorize` в `hub-backend`. Ядро генерирует RS256 JWT-токен на 60 секунд (`mint_grant`) и возвращает внутренний адрес апстрима в заголовке `X-Hub-Module-Upstream`. Nginx динамически перенаправляет запрос на этот адрес с токеном в заголовке `X-Hub-Access-Grant`. Модуль валидирует токен локально открытым ключом, а мгновенный отзыв прав проверяется по черному списку в Redis.

### 2. Детерминированный анти-галлюцинационный барьер в речевой аналитике (`EvidenceValidator`)
- **Сложность:** Галлюцинации LLM при автоматической оценке операторов: выдумывание непроизнесенных фраз или ложная фиксация нарушений, приводящая к искажению KPI персонала.
- **Реализация:** Внедрен строгий пост-процессинговый верификатор `EvidenceValidator`. Каждая находка модели обязана содержать точный `segment_id` и подстроку `quote`. Сервис программно проверяет фактическое наличие цитаты в исходном сегменте стенограммы:
  `if evidence.quote not in segment.text: raise EvidenceValidationError(...)`. При несовпадении результат отбраковывается и отправляется на повторную генерацию или помечается флагом расхождения для супервизора.

### 3. Отказоустойчивый распределенный планировщик задач на Redis ZSET с учетом часовых поясов
- **Сложность:** Надежная отправка отложенных напоминаний пассажирам без использования тяжелых брокеров и без риска потери расписания при перезапуске контейнеров или дублирования сообщений параллельными воркерами.
- **Реализация:** Спроектирован сервис `ReminderSchedulerService` на базе Redis Sorted Set (`reminders:scheduled`), где score — timestamp исполнения. Извлечение задач производится атомарным конвейером. Внедрена логика Safe-Time Scheduling с учетом часового пояса аэропорта (`Asia/Tashkent`), автоматическим сдвигом ночных уведомлений на утро и подавлением регулярных маркетинговых касаний при создании пассажиром персонального напоминания.

### 4. Неблокирующий конвейер ретроспективного пересчета аналитики (`ScenarioRescoreDispatcher`)
- **Сложность:** При изменении весов критериев оценки в админ-панели требуется пересчитать скоринг сотен исторических звонков без блокировки HTTP-воркеров и без перегрузки внешних LLM API.
- **Реализация:** Реализован фоновый диспетчер на примитивах синхронизации ОС (`threading.Thread`, `threading.Event`, `threading.Lock`). Диспетчер находится в спящем режиме и просыпается по сигналу обновления профиля. Промежуточные обновления профилей коалесцируются (схлопываются), а пересчет звонков выполняется батчами с контролем параллелизма, полностью изолируя критический путь обслуживания API от аналитической нагрузки.
